# APIキー・機密情報の露出チェック

サーバーサイド専用のシークレット(DB接続情報、決済APIの秘密鍵、メール送信サービスのAPIキーなど)がクライアントに配信されるファイル(HTML/JS/CSS/ビルド出力)に含まれていないか、また設定ファイルそのものが公開領域に置かれていないかを確認する。

## 大前提: 「公開されているキー」と「公開してはいけないキー」を混同しない

すべてのAPIキーが危険なわけではない。以下は**クライアントに見えて問題ない**設計のキーで、見つけても指摘不要:

- Google Analytics測定ID(`G-XXXXXXXXXX`)、Google Tag Manager ID(`GTM-XXXXXX`)
- ドメイン制限をかけたGoogle Maps APIキー(制限がかかっているかまでは通常コードから判断できないため、見つけたら「ドメイン制限がかかっているか確認してください」と添えるに留める)
- Stripeの publishable key(`pk_live_...`, `pk_test_...`)、reCAPTCHAのsite key など、名称に"public"/"publishable"を含み、サービス仕様として公開前提のキー

**危険なのは以下のように、本来サーバーサイドでのみ扱うべき値がクライアント配信物(HTML/JSバンドル/公開ディレクトリ配下)に紛れ込んでいるケース**:

- `sk_live_...`, `sk_test_...`(Stripeの secret key)
- `AIza...`だが用途がサーバー専用のAPI(制限されていないGoogle Cloud APIキー全般)
- `AKIA...`(AWSアクセスキーID)や、それに対応するシークレットアクセスキー
- DB接続文字列(`mysql://user:password@...`, `postgres://...`)
- SMTPのユーザー名・パスワード
- JWTの署名シークレット、セッションシークレット
- `.env`ファイルの中身がそのままJSにバンドルされている、あるいは`.env`ファイル自体がビルド出力(`dist/`, `public/`, `build/`等)にコピーされている

## グレーゾーン: ヘッドレスCMSのAPIキー(microCMSなど)

microCMSのような日本でよく使われるヘッドレスCMSのAPIキー(`X-MICROCMS-API-KEY`ヘッダーで送るキー)は、上記の「安全」「危険」のどちらにも単純に分類できないため、見つけたら権限の種類まで確認する。

- **GET専用(コンテンツ取得のみ)のキー**: ビルド時(SSG)にコンテンツを取得するだけなら、キー自体がクライアントの配信物に含まれないことが多い(ビルド時にしか使われないため)。ただしSPA的にクライアント側から直接fetchする実装だと、このキーがJSバンドルに埋め込まれて誰でも読めてしまう。microCMS公式ドキュメントも「識別されると第三者にコンテンツを操作される恐れがあるため取り扱いに注意」としており、GET専用でも野ざらしにしてよいわけではない(下書き状態のコンテンツが見えてしまう設定もありうる)。
- **POST/PUT/PATCH/DELETEの権限を含むキー**: 漏洩するとコンテンツの改ざん・削除に直結するため、**クライアント配信物に絶対に含めてはいけない**。見つけた場合は最優先で報告する。
- 確認の仕方: `X-MICROCMS-API-KEY`, `MICROCMS_API_KEY`, `microcms-management`などでgrepし、見つかった呼び出し箇所がビルド時(サーバーサイド/Node.js実行時)のみのコードか、ブラウザで実行されるコード(クライアントコンポーネント、ブラウザ向けJSバンドル)に含まれているかを区別する。後者であれば、そのキーが書き込み権限を持たないか(microCMS管理画面のAPIキー設定で確認が必要、コードからは判断できないことが多いので「書き込み権限が無いか管理画面で確認してください」と添える)を報告する。
- 同様の考え方は、他のヘッドレスCMS(Contentful, Sanity, Newt, Strapiなど)のAPIキーにも当てはまる。

## 探し方

1. **ビルド後の配信物を対象にする**: ソースコードにシークレットがあっても、実際にビルド出力(`dist/`, `build/`, `out/`, WordPressなら`wp-content/uploads/`などWeb経由でアクセス可能な場所)に含まれていなければ実害は小さい。逆にソースには無くても環境変数の埋め込み処理(Viteの`import.meta.env`、webpackの`DefinePlugin`、Next.jsの`NEXT_PUBLIC_`プレフィックスの有無など)によってビルド後のJSにサーバー専用の値が埋め込まれてしまうことがあるため、**必ずビルド後の実際のファイルをgrepする**。
2. 典型的なキーの接頭辞でgrep: `sk_live_`, `sk_test_`, `AKIA`, `-----BEGIN.*PRIVATE KEY-----`, `mysql://`, `postgres://`, `mongodb(\+srv)?://`, `X-MICROCMS-API-KEY`, `MICROCMS_API_KEY`。
3. `.env`, `.env.production`, `.env.local`などが`.gitignore`に含まれているか、かつビルド出力に誤ってコピーされていないかを確認する。
4. 静的サイトの場合、`.git/`ディレクトリがWebルート(公開ディレクトリ)にそのまま置かれていないか確認する。`.git/config`や過去のコミット履歴経由で機密情報が読み取れてしまう典型的な事故パターン。
5. WordPressの場合、`wp-config.php`がWebルート直下にある場合でも直接アクセスできないようになっているか(後述の`.htaccess`チェックと連動)、DB接続情報が`wp-config.php`以外にハードコードされていないかを確認する。

## 見つけた場合の報告の仕方

見つけたキーの**値そのものは報告に含めない**(レポートやログに秘密情報を転記しない)。「〇〇ファイルの△行目に、Stripeのsecret keyと思われる値がハードコードされています」のように、場所と種類だけを伝える。本物のキーかどうか・実際に有効かどうかの判断はプロジェクトの持ち主に委ねる。
